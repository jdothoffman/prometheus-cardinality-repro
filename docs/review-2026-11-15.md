# Independent review of the experiment results and the fleet-simulator direction

**Date:** 2026-11-15 · **Reviewed:** `docs/experiment-log.md`, `docs/next-steps.md`, `docs/proving-the-fix.md`, the 18 experiment reports in `./reports/`, and the uncommitted work on branch `feature/fleet-sim`.

**For the reviewing agent:** please check each numbered finding in section 3 against the raw data (section 2 says how) and say whether you agree. Where you agree, the doc fixes in section 5 apply. Nothing in the repo was changed by this review apart from adding this file.

## 1. Summary

- The numbers in the docs reproduce from the raw report data.
- The pipeline-side conclusions hold: cardinality creates pressure on the agent at every level, F1 removes it, and F5 is safe.
- The app-side conclusion ("contention is systematic, 3 of 3") is stated more strongly than the data supports. Four specific points are in section 3.
- The fleet-simulator direction is sound and the code builds. Its likely outcome and its dependence on agent sizing should be written down before the first run (section 6).

## 2. How the results were checked

Every report in `./reports/*.html` embeds its raw run data as `const R = {...}` in the page's script block. I parsed that JSON and recomputed the figures from these fields:

| Field | Contents |
|---|---|
| `R.points[]` | per second: `t`, `sent`, `ok`, `timeouts`, `p50`, `p95`, `p99`, `inFlight` |
| `R.replicaSamples[]` | per pod, every 2 s: `ts`, `cpuCores`, `throttledPct`, `gcHeapBytes`, `exportMaxMs`, `exportPoints`, `exportFailures`, `exportRetries`, `gcPausePct`, `gen2` |
| `R.pipelineSamples[]` | every 10 s: `alloyMemory`, `promMemory`, `headSeries` |
| `R.evidence.facts` | the report's own derived figures (`soakThrottleLate`, `soakP95Late`, …) |
| `R.evidence.charts[]` | Prometheus series, including "Alloy: OTLP in / remote_write failures" (accepted and refused points) |
| `R.evidence.terminations[]`, `R.evidence.events[]` | Kubernetes termination records and warning events |

Times below are seconds since `R.startedAtUnix`.

**Not checked:** the F1 histogram percentiles (89 ms against 63 ms) could not be re-queried, because Prometheus has been reset since. The bucket arithmetic agrees with them: 78% of requests under 50 ms and 100% under 100 ms gives an interpolated p95 of 88.6 ms.

## 3. Findings that differ from the docs

### 3.1 "CPU contention 3 of 3, +9 to +18 points" is overstated

**What the statistic is.** `soakThrottleEarly` and `soakThrottleLate` are the average, over polls, of the **most-throttled replica** in each poll (`Thr: g.Max(s => s.ThrottledPct)` in the `cpuByT` projection in `app/Report.cs`). The experiment log describes it as "share of time throttled at its 1-core limit", which reads as an average across pods. A max-of-four statistic is sensitive to single-pod spikes.

**What the average across pods shows** (mean of `throttledPct` over all pod samples in the window):

| L5 run | Docs: late quarter (worst pod) | Mean, t=420–960 | Mean, t=1030–1200 | CPU per pod, t=420–960 |
|---|---|---|---|---|
| Control | 33% | 9.8% | 9.4% | 0.785 |
| Hypothesis (1st) | 42% | 10.9% | 14.6% | 0.787 |
| Repeat 1 | 51% | 11.1% | 18.3% | 0.787 |
| Repeat 2 | 42% | 14.1% | 17.3% | 0.800 |
| F1 allow-list | 31% | 10.7% | 9.5% | 0.792 |
| F5 band | 21% | 8.6% | 5.9% | 0.780 |

The window t=420–960 starts after every pod has reached the 200k-series cap and ends before the stalls at t=973.

- **First run and repeat 1:** throttling matches control and F1 until about t=973, then steps up and stays up to the end of the run. Even on the docs' own worst-pod statistic, the t=420–960 window gives 33.6 and 33.7, against 29.9 for control and 33.9 for F1.
- **Repeat 2:** elevated from about minute 7 on, by about 4 points.
- **Noise:** there is one control run. F5 ended 12 points *below* control on the docs' statistic with nothing to explain it, so run-to-run drift is about as large as the claimed effect.
- **CPU:** per-pod CPU differs from control by 1–2%.

**My reading:** the direction is consistent (all three hypothesis runs end higher than control, F1 and F5), but the size is a few points of mean throttling, and most of the late-quarter difference in two of the three runs follows the t=973 event rather than preceding it.

### 3.2 The "+24 ms steady-state p95" is the stall averaged in

`soakP95Late` is the **mean** of per-second p95 over the last quarter. In the first L5 hypothesis run that quarter contains the stall (seconds at 1,340, 1,188, 868 and 780 ms).

| L5 run | Late p95, mean | Late p95, median |
|---|---|---|
| Control | 62.8 ms | 62.6 ms |
| Hypothesis (1st) | 86.6 ms | 63.6 ms |
| Repeat 1 | 72.9 ms | 63.7 ms |
| Repeat 2 | 63.8 ms | 63.6 ms |
| F1 | 62.9 ms | 62.8 ms |
| F5 | 62.9 ms | 62.8 ms |

The steady-state shift is about 1 ms, consistent across the three hypothesis runs. The experiment log's line "The steady-state difference is the stronger evidence: +9 points of throttling and +24 ms of p95" should go, along with the "+24 ms p95 at 80% load" in the "Shown" list.

### 3.3 Both L5 stalls began at the same second

Seconds with p95 above 100 ms:

- **Hypothesis (1st):** t=973 (142 ms), 974 (412), 975 (868), 976 (1,340), 977 (1,188), 978 (780), then a tail to about t=1020.
- **Repeat 1:** t=973 (134 ms), 974 (497), 975 (456), 976 (457), 977 (227), then a tail to about t=1015.
- **Repeat 2, control, F1, F5:** nothing near t=973.

Two independent runs degrading from the same second is unlikely to be chance. It points to a specific trigger about 16 minutes after the reset, which only hurts pods that are carrying the 200k-series state. The docs attribute the intermittency to timing ("it needs replicas to hit their CPU limit together").

What I could rule out from the data:

- **The load driver:** `sent` stayed at 1,898–1,908 per second through the stall.
- **Alloy:** memory flat at about 49 MiB, 0 points accepted and 0 refused throughout.
- **A gen2 GC:** the `gen2` delta is 0 on all four pods for t=974–987 in the first run.
- **The exports as the trigger:** latency rose at t=973, before the slow exports recorded at t=976.

What I could not identify is the trigger itself. In the two stalled runs Prometheus memory rose 15–25 MiB in the minute after the stall, and stayed flat in repeat 2. That may be an effect rather than a cause.

### 3.4 The agent was not pushing back when the app stalled

Insight 11 says a refusing or slow agent keeps the app retrying, and "that caused the L4 outage". The data doesn't show the agent in that state at the time of any stall.

**L5 hypothesis runs (all three):**

- Alloy was OOMKilled 5–6 times in the first 4–8 minutes (`terminations[].restartCount` of 5, 6 and 5, with `finishedAt` inside each run).
- Alloy refused points only early: last non-zero refused value at t=115, t=140 and t=385.
- From then to the end of the run, Alloy accepted 0 and refused 0 points, at 48–58 MiB.
- App exports in that period failed in 30–70 ms with `exportRetries` at 0.
- The stalls at t=973 fall in this period.

**L4 outage (t=183):**

- `alloyMemory` is missing (container not running) for most samples from t=144 to t=224.
- Accepted and refused points both end at t=115.
- So Alloy was mid crash-loop, not "alive but refusing or slow".

**What that leaves:** the common factor in the runs with app-side effects is each pod holding 200k series and a 460 MiB heap, and collecting them every 10 s. That is a cost of cardinality inside the SDK, not of agent back pressure. It is still removed by F1.

**A confound:** the claim that the agent profile decides whether the app is hurt compares L1–L3 (normal agent, 60–70% load, 3-CPU nodes) with L4–L5 (constrained agent, 70–80% load). There is no L5-load run with the normal agent.

**Unknown:** why exports fail in 30–70 ms for 13 minutes while Alloy is up and counting nothing. The HTTP status of failed exports isn't recorded, and `exportBytes` keeps the last non-zero value, so it can't show whether a request was sent.

## 5. Doc corrections

1. **Experiment log, TL;DR and section 4 "Reading it":** replace "CPU contention is systematic, +9 to +18 points" with the worst-pod definition and the mean-across-pods figures from 3.1, and note the single control and the F5 drift.
2. **Experiment log, "What it does and doesn't show" and the L5 interpretation:** remove "+24 ms p95" as steady-state evidence (3.2).
3. **Experiment log, L5 section:** record that two stalls started at t=973 and that the trigger is unidentified (3.3).
4. **Experiment log, insights 5, 10 and 11, and the L4 mechanism paragraph:** the agent was crash-looping or idle at the time of each stall, so "refusal caused the outage" is not supported (3.4). `agent/config-constrained-protect.alloy` carries the same claim in its header comment.
5. **L5 repeats table, Alloy row:** repeat 1 and repeat 2 show "1 restart" and none. Kubernetes records show 6 and 5 OOMKills. `alloyRestartsDelta` undercounts when Alloy is down. The "0–5 restarts" cell in `proving-the-fix.md` should read 5–6.
6. **Histogram series cost:** the F1 histogram had 11 boundaries, which is 12 buckets plus sum and count, so 14 series per label combination: 160 × 14 × 4 = 8,960, not 7,680. The "about 12 series per histogram" estimate in `proving-the-fix.md` has the same slip (10 boundaries give 13).
7. **Production pivot:** none of the three docs record that production already buckets response time. `proving-the-fix.md` still opens with the float label as "the problem in one line", and `next-steps.md` doesn't mention the change of suspect to pod and appended labels.

## 6. Review of the fleet-simulator work (`feature/fleet-sim`, uncommitted)

**What it does:** adds an `APP_ROLE=fleet` mode (`app/Fleet.cs`, `k8s/fleet.yaml`) in which each replica runs 150 simulated pods. Each has its own `MeterProvider`, resource and OTLP exporter, uses its own pod name as the `pod` label and a banded `response_time`, and exports on its own phase. It also adds `make prod-pods` (`VIRTUAL_PODS=1`), reshaped histogram boundaries, fleet-aware control matching and a fleet finding in the report.

**What's good:**

- A scratch copy of `app/` builds with 0 warnings and 0 errors.
- The fleet runs on its own tainted node, so it can't take CPU from the replicas under test.
- The per-pod meter name is a justified workaround, and it gives the protect rule something to match.
- `FindControl` picks a control with the same labels and no fleet, so the fleet is the only difference.
- The new boundaries (`…, 0.04, 0.05, 0.06, 0.07, 0.08, 0.1, …`) put p95 (about 63 ms) in a 10 ms bucket, which addresses the 89 ms against 63 ms finding.

**Concerns, most important first:**

1. **The likely outcome is "Alloy struggles, the app is unaffected".** With bounded labels and `VIRTUAL_PODS=1`, each real replica exports a few hundred series. A refusing agent then costs the app almost nothing. Every app-side effect so far needed large per-pod SDK state (3.4). That result would be informative, since it would say agent overload alone can't explain degraded response times under these OTel semantics. Write the pass/fail criteria down before the first run, as decision 3 in `next-steps.md` did for L5.
2. **Agent sizing decides the result.** 300 pods × about 580 points every 10 s is about 17k points/s. F5 drew refusals at 6.3k points/s on the 250m / 384 Mi agent. Without production's Alloy limits and real per-pod series counts, the run can only show that an undersized agent is overwhelmed. Scale the fleet and the agent from production figures.
3. **The current suspect isn't modelled.** There is no knob for labels the observability team appends (agent-side enrichment or SDK resource attributes). The fleet's series are also dropped before Prometheus, so churn (`FLEET_CHURN_SECONDS`) and aggregate cost at Prometheus are not measured. The experiment tests the Alloy hop only.
4. **"Bucketed" is assumed to mean 5 bands.** If production rounds to 2 or 3 decimals, series grow during an incident (the precision table in `proving-the-fix.md`). `FLEET_RESPONSE_TIME` supports both; the default needs confirming.
5. **Churn can block.** `Churn()` disposes about 30 pods one after another on the timer thread, and each dispose flushes an export with an 8 s timeout. With a slow agent that can take minutes and overlap the next timer tick.
6. **`FLEET_EXTRA_SERIES=100` is a guess.** Calibrate it against a real pod's series count.

## 7. Suggested next steps

1. Apply the doc corrections in section 5.
2. Re-test the run-A failure mode with production's real `CardinalityLimit` settings. A raised limit across many instruments reserves most of the GC heap at startup, never shows as `OOMKilled`, and doesn't depend on any bad label, so it survives the finding that production already buckets response time.
3. Get the production facts before sizing the fleet run: Alloy CPU and memory limits, series per pod, how response time is bucketed, which labels are appended and where.
4. Record the HTTP status code of failed exports in `ExportHttpHandler`, and whether a request was sent.
5. Run one longer L5 hypothesis (40 min or more) to see whether the t=973 event recurs on a period, and add a second L5 control to measure run-to-run noise.
6. Run L5 with the normal agent to separate agent profile from load level.
